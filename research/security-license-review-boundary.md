## Decision

**Require a reproducible pre-publish gate covering code, dependency resolution, licenses, secrets, basic threat cases, package contents, and source/release integrity. Do not perform or claim a formal penetration/privacy/compliance audit yet. Escalate to a full audit as soon as there is evidence of production promotion, PyPI/public package release, multi-tenant or cross-customer use, or processing of real user PII/confidential memory data.**

The practical gate is a release blocker: no unresolved high/critical SAST finding, known exploitable dependency, incompatible license, credential, package-content leak, cross-profile read, unsafe outbox exposure, or unexplained supply-chain discrepancy may remain. Medium findings require a documented disposition; false positives must have an owner and rationale.

Neither is security evidence. Together they prove only the fake/stdlib/modelled boundaries described by their respective evidence files; they do not prove live HTTP behavior, authentication, package installation, SQLite crash safety, authorization, supply-chain integrity, or license completeness.

### E. Basic threat-model checks now

#### Fixed Hindsight destination contract (release gate)

The successor must not accept an arbitrary URL. Its configuration contains one required **Hindsight origin allowlist entry**, and configuration loading fails closed if it is absent, malformed, duplicated, or has more than one origin. The entry is an exact tuple:

```text
scheme = https
hostname = <one configured DNS name, canonicalized with IDNA2008 UTS #46 transitional=false, lower-case, trailing dot removed>
port = 443
base_path = <one configured, absolute API prefix; no path traversal or query/fragment>
```

The hostname is a DNS name, never an IP literal, and its canonical ASCII form is the only approved identity. There is no default hostname, wildcard, suffix match, alternate port, HTTP mode, or “localhost” mode. The approved destination is the exact origin `https://<canonical-host>:443` plus the configured API prefix; requests may use only the fixed Hindsight API paths registered by the adapter beneath that prefix. A URL supplied by a memory item, bank/profile value, response, redirect, environment proxy, or request parameter is never allowed to replace any tuple member. If a deployment genuinely needs another Hindsight origin or port, an administrator must issue a new reviewed configuration and rerun this gate; it is not a runtime override.

The endpoint/allowlist configuration is **authenticated and admin-only**. Reconcile this with issue/07 by making one protected profile configuration/secret source authoritative for the complete endpoint tuple, TLS policy, and proxy-disabled policy; do not merge competing endpoint fields from ordinary Hermes config, environment variables, provider arguments, memory metadata, request parameters, or runtime overrides. The precedence is therefore: (1) the authenticated protected source, if present and schema-valid; (2) no fallback. A missing, duplicated, partially overridden, malformed, unsigned, or unauthorized value is a startup error, not a default. The owner and group must be the profile/service identity (or an explicitly documented administrator identity), permissions must be restrictive (no group/world write), and the loader must reject symlinks, non-regular files, unexpected ownership, and unverifiable permissions. The source must be authenticated/integrity-protected: either an administrator-controlled secret/config store with its documented authentication and integrity guarantee, or the following canonical document with an administrator-controlled MAC/signature and pinned verification key. A file that is merely readable is not an authenticated source.

**Authenticated document contract (version 1):** the signed/MACed payload is UTF-8 JSON serialized with RFC 8785 JSON Canonicalization Scheme (JCS): no duplicate names, no insignificant whitespace, no alternate numeric/string encodings, and UTF-8 only. It contains `schema_version: 1`, `key_id`, `config_id`, integer `sequence`, RFC 3339 UTC `issued_at`, `not_before`, `expires_at`, and the complete endpoint/TLS/proxy payload; the authentication envelope is outside the payload and covers the exact canonical payload bytes with domain separator `hermes-tiered-memory/config/v1\0`. Approved algorithms are `HMAC-SHA-256` for a secret-store/MAC deployment and `Ed25519` for a detached-signature deployment; reject every other or unspecified algorithm. The `key_id` selects a pinned, administrator-authorized verification key, and unknown, revoked, or wrong-purpose keys fail closed. Rotation publishes a new key before use, accepts old and new keys only during a documented overlap, then revokes the old key; each rotation is a new authenticated release event.

Freshness is checked before any side effect: require `not_before <= now <= expires_at`, a bounded documented clock-skew allowance (at most five minutes), and a strictly increasing `sequence` per `config_id`. An identical digest/sequence is idempotent; a lower sequence, expired document, changed payload at the same sequence, or reuse of a revoked key is a rollback/replay and is rejected. The highest accepted sequence and payload digest must be stored durably before activation, so restart cannot accept an older snapshot. Ordinary environment/config values may supply only non-security settings and must be rejected if they attempt to replace or augment this tuple. The Hindsight API credential is separate, injected through the supported secret mechanism, and must not appear in the URL, logs, proxy configuration, or process arguments. The release record must name the canonical hostname, port, base path, TLS trust policy, source identity, ownership/permission rule, and integrity/authentication method; this source-only report intentionally contains no real deployment hostname or credential.

**Atomic reload state machine:** `UNINITIALIZED -> VALIDATING -> ACTIVE` on a fully parsed, authenticated, fresh, schema-valid document; validation performs no DNS, socket, proxy, TLS, or HTTP activity. From `ACTIVE`, a reload enters `VALIDATING` while the last-known-good immutable snapshot remains the only serving snapshot; only after all checks and durable sequence/digest recording succeed does one atomic pointer/generation swap install the new snapshot and return to `ACTIVE`. Any invalid, stale, replayed, unauthorized, or unverifiable reload is discarded: retain the last-known-good snapshot and remain `ACTIVE` (or enter `QUIESCED/FAIL_CLOSED` if no snapshot has ever been accepted). There is no network activity on a failed reload, and in-flight operations continue using their captured generation. Recovery is an explicit authenticated administrator reload/restart with a newer valid sequence; automatic retries may re-read/validate local authenticated bytes but may not contact the network or bypass freshness. A failed reload must never make a previously active configuration unusable.

Required no-network-before-auth tests: with the protected source absent, unreadable, wrong-owner, group/world-writable, symlinked, duplicate-keyed, MAC/signature-invalid, stale/replayed, or overridden by endpoint environment/config/provider input, startup/reload must fail before DNS, socket, proxy, TLS, or HTTP activity; instrument each boundary and assert zero calls. Test valid initial load, valid atomic replacement, invalid replacement retaining the old generation, no-LKG quiescence, restart rollback rejection, and key rotation overlap/revocation. A valid protected source must be accepted only through the authenticated administrator path, not a request-scoped override.

#### TLS authentication invariant

TLS is authenticated against the selected trust store, not merely encrypted. The client must build a certificate chain to a configured trust anchor using normal chain validation (validity period, key usage/EKU, critical extensions, and signature algorithms), and must perform hostname verification against the canonical IDNA ASCII hostname from the endpoint tuple. SNI must be that same canonical hostname. `verify=False`, disabled certificate checks, post-connect certificate exceptions, opportunistic HTTP, and silent fallback to an unverified transport are forbidden. The client must not accept `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, or equivalent ambient CA/environment overrides, and must not let ordinary config/provider input select a trust store. The default trust store is the explicitly selected runtime/system store recorded in release evidence. A custom CA is permitted only when an authenticated administrator configures a specific regular file or secret-store object, with ownership/permissions and integrity verification, an explicit replacement/augmentation decision, and a recorded fingerprint; it is not fetched over the network and cannot be changed per request. Tests must cover an untrusted issuer, expired/not-yet-valid chain, wrong hostname, missing EKU, altered custom-CA bytes/fingerprint, ambient CA override, and valid chain/SNI success, while asserting no HTTP request is sent on TLS-authentication failure. **Actual certificate-chain, hostname/SNI, trust-store provenance, and custom-CA fingerprint evidence is UNVERIFIED in this source-only report and remains so until retained test/deployment output records it; the contract is not a claim that TLS was exercised.**

#### Exact HTTP route, method, path, and authority invariant

Route policy is release-blocked until it is bound to one retained, immutable OpenAPI artifact for the selected Hindsight source: full upstream commit SHA (not a tag or short SHA), retrieval URL, media type, UTC retrieval timestamp, SHA-256, and the exact operation entries used by the adapter. The evidence must also record the **concrete configured `base_path`** (an actual absolute prefix selected by the administrator, never a placeholder at release time) and the bank-ID encoding rule: one validated path segment, canonical single percent-encoding with uppercase escapes, permitted character set, and explicit rejection cases for separators, dot segments, controls, and double encoding. The OpenAPI artifact and these derived route/authority decisions are a single review unit; a changed commit/hash, base path, or encoding rule requires a new review. The source-only report has not retained this artifact or a concrete deployment base path, so route compatibility and live integration are **UNVERIFIED** and no route claim below is evidence of a live server.

After that gate passes, the adapter may use only the exact `(method, path)` operations extracted from that pinned artifact, rendered beneath the recorded base path. It must not invent routes from prose, generated-client assumptions, a floating/live API response, or a framework default. The release evidence must reproduce the concrete table, including whether readiness is in scope; if it is not, omit it rather than broaden the allowlist. Every unlisted method/path (including `OPTIONS`, `TRACE`, `CONNECT`, and framework fallbacks) is rejected.

Build request targets from structured path segments only: decode nothing after validation, percent-encode each segment once with the fixed evidence-backed safe set, use uppercase percent escapes, and reject NUL/control bytes, backslashes, `.`/`..` segments, encoded separators, encoded dot segments, double-encoding, query/fragment injection, and non-canonical spellings. Reject absolute-form request targets (`http://other/`, `https://other/`) and authority-form targets except a separately reviewed proxy CONNECT path; use origin-form paths only. The direct `Host` header must be exactly the canonical hostname and `:443` authority (with no userinfo, alternate port, whitespace, duplicate Host, or trailing-dot variant), and must equal TLS SNI, connector authority, and the protected configured tuple. Never derive Host, path, SNI, or authority from a redirect, response, memory content, bank/profile input, or URL parameter.

For direct connections, reject any request whose parsed request-target authority, Host, SNI, connector authority, or configured tuple differs. If a reviewed proxy mode is ever enabled, CONNECT is allowed only to the exact configured proxy authority, its target must be the exact canonical Hindsight authority, and the tunneled origin-form request must still satisfy the pinned OpenAPI path and direct Host/SNI rules. All other CONNECT/request-target combinations are rejected. Tests must cover absolute-form, authority-form, duplicate/whitespace Host, alternate port, trailing-dot Host, Host/SNI mismatch, CONNECT mismatch, encoded traversal/separators, non-canonical percent escapes, query/fragment smuggling, unlisted method/path, and exact allowlisted requests.

#### Address, DNS, connector, proxy, and redirect invariant

For every outbound request, endpoint validation must be enforceable, not a best-effort DNS check. Parse the configured origin strictly, canonicalize IDNA before comparison, reject userinfo/fragments/control characters/ambiguous ports and all IP-literal spellings (decimal, octal, hexadecimal, integer, mixed IPv4, bracket tricks, IPv4-mapped IPv6), and reject any address that is not globally routable. Explicitly reject IPv6 zone/scope identifiers in every input and resolver result (`%25eth0`, `%eth0`, numeric scopes, and equivalent decoded forms); a hostname or address with a zone ID is never normalized into an approved destination. Use a **controlled resolver/connector pattern**: resolve the canonical hostname through an injected resolver; follow and validate the complete bounded CNAME chain and every A and AAAA answer; re-check the resulting address set immediately before connect; normalize each resolver sockaddr to a scope-free numeric address and discard its port/flowinfo/scope_id before policy comparison and connection; connect only to one of those validated numeric addresses while passing the original canonical hostname to TLS for SNI and certificate hostname verification; and prevent a second unconstrained resolver lookup in the HTTP client. A resolver result/connection race must fail closed, not fall back to the system resolver. The implementation must test that scoped sockaddr input is rejected rather than accidentally converted into a link-local or interface-bound connection, and that accepted numeric addresses contain no scope suffix.

The deny policy must reject the following IPv4 ranges, including their IPv4-mapped IPv6 forms: `0.0.0.0/8` (current network/unspecified), `10.0.0.0/8` (private), `100.64.0.0/10` (shared/CGNAT), `127.0.0.0/8` (loopback), `169.254.0.0/16` (link-local), `172.16.0.0/12` (private), `192.0.0.0/24` (IETF special use, including NAT64/DNS64 discovery exceptions), `192.0.2.0/24` (documentation), `192.88.99.0/24` (6to4 relay anycast), `192.168.0.0/16` (private), `198.18.0.0/15` (benchmarking), `198.51.100.0/24` (documentation), `203.0.113.0/24` (documentation), `224.0.0.0/4` (multicast), and `240.0.0.0/4` (reserved/future use, including limited broadcast). Apply the current IANA IPv4 Special-Purpose Address Registry as a deny-by-default supplement so newly assigned special-purpose blocks cannot become reachable by policy omission.

The deny policy must reject these IPv6 categories/prefixes: `::/128` (unspecified), `::1/128` (loopback), `::ffff:0:0/96` (IPv4-mapped), `::/96` (IPv4-compatible/deprecated), `64:ff9b::/96` and `64:ff9b:1::/48` (NAT64 translation), `100::/64` (discard-only), `2001:0000::/32` (Teredo), `2001:0002::/48` (benchmarking), `2001:0010::/28` and `2001:0020::/28` (ORCHID/ORCHIDv2), `2001:db8::/32` (documentation), `2002::/16` (6to4 transition), `fc00::/7` (unique-local), `fe80::/10` (link-local), and `ff00::/8` (multicast). Also reject any address classified by the IANA IPv6 Special-Purpose Address Registry as not globally reachable; do not rely solely on a language runtime's `is_private` flag.

Proxies are disabled by default, including `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, lowercase variants, proxy config files, and automatic proxy discovery. Redirects are disabled by default. If a reviewed mode enables them, every hop must be HTTPS and an exact match for the configured canonical scheme, hostname, port, and API prefix; cross-origin, alternate-port, userinfo, downgrade, and credential/proxy-policy changes are rejected.

**Data-at-rest boundary:** the package and publish set must contain no real outbox, SQLite database/WAL, logs, backups, memory payloads, or credentials. For synthetic disposable tests, restrictive permissions, crash inspection, retention/compaction, and deletion behavior are package/test obligations. If a deployment uses the provider with real data, the outbox/WAL is a data store: its OS permissions, encryption or compensating controls, backup scope/access, retention/deletion, quarantine copies, and operator access must be specified by the deployment owner. ## 4. Precise full-audit trigger

Escalate from this practical review to a formal security/privacy/license/supply-chain audit on the **first verified occurrence** of any condition below, and do not treat a clean pre-publish gate as a waiver:

For this decision, “private” means an explicitly recorded trust-domain inventory, not merely a private repository, RFC1918 network, or non-public URL. The inventory must name the administering organization/team, permitted hosts and deployment accounts, artifact registries, and CI identities/service accounts (including the exact repository/workflow identities allowed to build or publish). A host, team, CI identity, registry, or operator outside that inventory is external. Installation, source/artifact access, build, signing, or publication involving any such external party is an external-distribution/security-boundary event and triggers the formal audit; a secret or network path that happens to remain private does not make it internal. The owner must keep this inventory with the release evidence and re-evaluate it whenever hosting, maintainers, CI, or publication targets change.

1. **Production promotion:** the real composite is enabled in any production Hermes profile, points at a live Hindsight service, or writes/reads non-test memory data.
2. **External installation or public package release:** a wheel/sdist is uploaded to PyPI or another public package index, or an artifact/source is distributed for installation, building, signing, or operation by any person, organization, host, registry, CI identity, or trust domain outside the explicit private inventory above. This trigger applies even if the artifact is not publicly indexed.
3. **Multi-tenant/cross-customer use:** more than one independent user, customer, organization, or trust domain can share the service, bank namespace, endpoint, or package deployment. This is an unconditional trigger, including when the artifact is private, the tenants are operated by the same team, or isolation is asserted but not independently audited.
4. **Sensitive-data processing:** the provider handles any real user PII, confidential business data, regulated data, secrets, or memory data subject to contractual retention/deletion obligations. This is an unconditional trigger regardless of repository visibility, network reachability, host ownership, or whether the data is encrypted at rest.
5. **Security-boundary expansion:** the plugin gains privileged filesystem/network access, server-side administrative APIs, arbitrary tool execution, a new process/sidecar, custom crypto, remote code/plugin loading, or a change that can bypass profile/bank authorization.
6. **Material supply-chain/license event:** a new non-permissive/ambiguous license, a critical/high exploitable dependency finding, a compromised/revoked artifact, a package-signing/provenance failure, copied upstream code, or a dependency/source change outside the pinned review.
7. **Incident evidence:** a credential leak, cross-profile read, unexpected egress, memory disclosure, tampered artifact, or unexplained outbox data-loss/corruption event.

At the trigger, the formal audit should include independent code review/penetration testing, threat modeling and abuse cases, tenant authorization and race testing, secret/PII lifecycle and backup review, dependency/SBOM/provenance verification, license counsel review, live deployment configuration review, and a documented remediation/retest cycle. The exact compliance framework depends on the actual data and customers; it cannot be chosen honestly before those facts exist.
